House rules — every problem, no exceptions

  • Test with 200 records. Insert them in one DML call inside Test.startTest(). If it only works for one record, it doesn't work.
  • One trigger per object, logic in a handler class. The trigger file is 3–10 lines that delegate.
  • No SeeAllData=true. Build your own data in every test.
  • Assert limits, not just outcomes. Assert.isTrue(Limits.getQueries() <= 2) after your bulk run catches SOQL-in-loop regressions forever.
  • Ship the test in the same sitting as the code. That's the habit that separates admin-who-codes from developer.
01

Triggers, the daily bread

80% of real Apex tickets live here.

1 · Rollup without DLRS
Foundationtrigger handlermapsaggregate SOQLbulkification

The ticket: Partner managers want Active_Contact_Count__c on Account to always equal the number of that Account's Contacts where Active__c = true. No managed packages, no DLRS — pure Apex.

Build
  • Trigger on Contact for insert, update, delete, and undelete, delegating to ContactTriggerHandler.
  • Recalculate with one AggregateResult query per transaction, keyed by AccountId.
  • On update, only recalc if Active__c or AccountId actually changed.
The trap

When a Contact is reparented (AccountId changes), both the old and the new Account need a recalc. Collect Account IDs from Trigger.oldMap and Trigger.newMap. Almost every first attempt misses the old parent.

Done when
  • A test moves 200 Contacts between two Accounts in one DML and both counts are right.
  • Undeleting a Contact from the Recycle Bin bumps the count.
  • Whole transaction uses ≤ 2 SOQL queries, asserted in the test.
2 · Lock the closed record
FoundationaddErrorcustom permissionsTrigger.oldMap

The ticket: Once an Opportunity hits Closed Won, nobody edits Amount or CloseDate — except users holding a custom permission called Edit_Closed_Opportunities. Validation rules got too tangled; do it in Apex.

Build
  • Before-update logic that compares old vs. new values and calls record.addError() on violations.
  • Gate the bypass with FeatureManagement.checkPermission('Edit_Closed_Opportunities') — never a profile-name string check.
  • Create the Custom Permission and a Permission Set in TrentDev; assign it to yourself to test the bypass live.
The trap

addError in a bulk update must block only the offending records — the clean ones in the same batch must still save. Test with a mixed batch and partial-success DML (Database.update(records, false)) to prove it.

Done when
  • Mixed batch of 200 (half violating) saves exactly the clean half.
  • System.runAs tests cover both a blocked user and a permitted one.
3 · Duplicate junction blocker
Working leveljunction objectsin-memory dedupecomposite keys

The ticket: You have a junction object Program_Enrollment__c linking Contact to Program__c. Users keep creating duplicates. Block any insert that would create a second enrollment for the same Contact + Program pair.

Build
  • Before-insert handler that builds a composite key (ContactId + '|' + ProgramId) per record.
  • One query for existing enrollments matching any incoming key; addError on collisions.
The trap

Two duplicates inside the same insert batch won't be caught by querying the database — neither exists yet. You need a second check: dedupe within Trigger.new itself using a Set of keys as you iterate. This exact miss is a classic code-review catch.

Done when
  • A test inserting the same pair twice in one list blocks the second.
  • A test inserting a pair that already exists in the database blocks it.
  • Stretch: also enforce it with a unique text field (external ID) and explain in a comment which defense is authoritative and why you keep both.
02

SOQL & collections under pressure

Where governor limits are won or lost.

4 · The escalation summary
FoundationMap<Id, List<>>GROUP BYone-pass building

The ticket: Support leadership wants a method the team can call from anywhere: given a set of Account IDs, return each Account's open Case count and its single oldest open Case. One class, two public methods.

Build
  • Map<Id, Integer> getOpenCaseCounts(Set<Id>) using one aggregate query (COUNT(Id) ... GROUP BY AccountId).
  • Map<Id, Case> getOldestOpenCase(Set<Id>) — one query ordered by CreatedDate ASC, then keep only the first Case you see per Account while iterating.
  • No loops containing SOQL. No second pass over the query results.
The trap

The oldest-case method tempts you toward a query per Account. The idiom to burn in: query everything ordered, iterate once, and use map.containsKey() to keep only the first hit. This pattern shows up weekly in real work.

Done when
  • Works for an Account with zero cases (absent from map, not null-crashing).
  • Test asserts exactly 1 query per method call via Limits.getQueries().
5 · Fix this real, bad trigger
Working levelrefactoringSOQL-in-loopDML-in-loop

The ticket: This trigger is live in "production" and dies with Too many SOQL queries: 101 every time Data Loader runs. Deploy it to TrentDev, reproduce the failure with a 200-record insert, then refactor it into a handler that passes.

trigger TaskOnNewContact on Contact (after insert) {
    for (Contact c : Trigger.new) {
        Account a = [SELECT Id, OwnerId, Type FROM Account
                     WHERE Id = :c.AccountId];
        if (a.Type == 'Partner') {
            Task t = new Task(
                Subject = 'Welcome call: ' + c.LastName,
                WhoId = c.Id, OwnerId = a.OwnerId,
                ActivityDate = Date.today().addDays(3));
            insert t;
        }
    }
}
The trap

Beyond the obvious query-and-DML-in-loop: the original crashes on Contacts with a null AccountId — the query returns nothing and the assignment throws. Your refactor has to survive orphan Contacts. Reproducing the failure first is part of the rep; read the debug log and find the limit line.

Done when
  • 200 Contacts (some with null AccountId, some non-Partner) insert cleanly: 1 query, 1 DML.
  • You've kept a copy of the before/after debug logs — that's your interview story.
03

Async Apex

Nightly jobs and anything touching an API.

6 · The nightly stale-partner sweep
Working levelDatabase.BatchableSchedulablestateful counters

The ticket: Every night, flag Accounts of Type 'Partner' with no completed Activity in 120 days by setting Engagement_Status__c = 'Dormant', and clear the flag on any that have re-engaged. Log a one-line summary when done.

Build
  • One class implementing both Database.Batchable<SObject> and Schedulable.
  • Database.Stateful to count flagged/unflagged across batches; report both in finish().
  • Schedule it from Anonymous Apex with a CRON string you write by hand (1 a.m. daily) — no copy-paste.
The trap

"No activity in 120 days" is not queryable in the batch's start locator without a semi-join that gets expensive. Decide: NOT IN (SELECT ...) anti-join vs. querying activities in execute() per chunk. There's a defensible answer either way — write a comment defending yours. Also: Test.startTest/stopTest runs exactly one batch chunk, so your test data must fit one scope.

Done when
  • Test proves both directions: a dormant account gets flagged, a re-engaged one gets cleared.
  • It's actually scheduled in TrentDev and you can find it under Setup → Scheduled Jobs.
7 · Queueable sync after save
Working levelQueueableAllowsCalloutstrigger → async handoff

The ticket: When a Partner Account's Tier__c changes, POST the Account's Id, Name, and new tier as JSON to an external partner-portal API. Triggers can't make callouts, so architect the handoff.

Build
  • After-update handler collects changed Accounts and enqueues one Queueable implementing Database.AllowsCallouts carrying the whole list — never one job per record.
  • Endpoint behind a Named Credential (point it at https://httpbin.org in TrentDev, POST to /post).
  • On non-200, write an Integration_Log__c record with the payload — never swallow the failure silently.
The trap

200 Accounts updated = 1 enqueued job, not 200 — assert Limits.getQueueableJobs() == 1. And a callout body over ~100 records may need chunking: have the Queueable process N and re-enqueue itself for the rest. Chained enqueues throw in tests unless the chain check is guarded with Test.isRunningTest().

Done when
  • Test with an HttpCalloutMock covers 200-success and 500-failure paths; failure produces a log record.
  • One live run in TrentDev shows the httpbin echo in the debug log.
04

Integration

The work that gets you pulled into architecture meetings.

8 · Outbound callout, done properly
Working levelHttpRequestJSON.deserializewrapper classesHttpCalloutMock

The ticket: Build ZipLookupService.getCityState(String zip) that calls https://api.zippopotam.us/us/{zip} and returns a typed result object — city, state, or a structured error. This is the reusable-callout-wrapper pattern you'll copy for every future integration.

Build
  • Inner wrapper classes matching the JSON shape; deserialize with JSON.deserialize into them — no Map<String, Object> spelunking.
  • Handle 404 (bad zip), non-200, and a timeout (setTimeout, catch CalloutException) as distinct outcomes in the returned result object — the caller should never need try/catch.
  • A single HttpCalloutMock class that can be configured per-test to return any status/body.
The trap

The API's JSON key is "post code" — with a space. You can't name an Apex property that, so you'll hit the deserialize-vs-untyped-parse decision every real integration eventually forces. Solve it (parse untyped for just that field, or drop the field) and comment why.

Done when
  • Four tests: success, 404, 500, timeout — each asserting the typed result, not just "no exception."
  • One anonymous-Apex live call works after you add the Remote Site Setting / Named Credential.
9 · Inbound REST endpoint
Stretch@RestResourceupsert semanticsstatus codes

The ticket: A partner's system needs to push lead referrals into Salesforce. Expose POST /services/apexrest/referrals accepting a JSON array of referrals (email, name, company, partner code). Upsert Leads on email; respond with per-record results.

Build
  • @RestResource class with a request/response wrapper: each input row gets back {email, status: created|updated|error, message}.
  • Set real status codes via RestContext.response.statusCode: 200 all-good, 207-style partial (or 400 with detail) when some rows fail, 400 for unparseable body.
  • Malformed JSON must return a clean error body, never an unhandled exception page.
The trap

Partial success is the whole problem. Use Database.upsert(leads, Lead.Email, false) and walk the Database.UpsertResult array to build per-row responses — index alignment between inputs and results is on you, and it breaks the moment you filter the list before DML without tracking the mapping.

Done when
  • Tests build RestContext.request by hand and cover clean, mixed, and garbage payloads.
  • You've hit the real endpoint in TrentDev once with curl or Workbench and read the response.
10 · Invocable Apex for Flow
Foundation@InvocableMethod@InvocableVariableflow bulkification

The ticket: Admins want Flows to fetch "days since last completed activity" for a record. Build an invocable action they can drop into any record-triggered Flow.

Build
  • Request class (recordId) and response class (daysSince, hasActivities) with @InvocableVariable(required=true) and honest labels/descriptions — admins read those.
  • The method takes List<Request> and returns List<Response> in the same order.
The trap

When a record-triggered Flow fires on a bulk save, Salesforce hands your method all interviews as one list. If you wrote it single-record-minded with a query inside a loop, a Data Loader run detonates it. One query for all requests, one pass to answer. Also: output order must match input order — Flow maps by index.

Done when
  • Test calls it with 200 requests and asserts 1 query.
  • You built an actual Flow in TrentDev that uses it and displays the result — see it from the admin's side.

Testing & legacy rescue

What senior devs actually spend their week on.

11 · Build the TestDataFactory
Foundation@IsTest utilitiesbuilder methodsrefactoring tests

The ticket: Your tests from problems 1–10 all hand-roll Accounts and Contacts. Build one @IsTest public class TestDataFactory and refactor at least three earlier test classes to use it.

Build
  • Methods like createPartnerAccounts(Integer n, Boolean doInsert) — count-parameterized, insert-optional, returning the list.
  • A graph method: createAccountWithContacts(Integer nContacts) for the common shape.
  • Sensible defaults for every required field so callers only override what the test is about.
The trap

The doInsert flag matters: tests that assert trigger behavior need uninserted records to insert inside Test.startTest(), while setup data should insert immediately. Factories without the flag push everyone back to hand-rolling. Also decide where @TestSetup fits alongside the factory — write your rule of thumb as a class-level comment.

Done when
  • Three refactored test classes still pass and each got shorter.
  • Someone could add a new object to the factory by pattern-matching your existing methods.
12 · The recursion bomb
Stretchtrigger recursionstatic guardstesting someone else's code

The ticket: This trigger shipped with zero tests. First write tests that expose its bugs (they should fail against the code as-is), then fix the code until they pass. Deploy it to TrentDev exactly as written first.

trigger AccountTierSync on Account (after update) {
    List<Account> toUpdate = new List<Account>();
    for (Account a : Trigger.new) {
        if (a.Tier__c == 'Gold') {
            toUpdate.add(new Account(
                Id = a.Id,
                Support_Level__c = 'Premium',
                Last_Tier_Change__c = System.now()));
        }
    }
    update toUpdate;   // same object, same trigger...
}
The trap

There are at least two bugs: the update re-fires the trigger (recursion — it only halts because Last_Tier_Change__c keeps changing until limits kill it), and non-Gold accounts never get their Support Level downgraded, which is silently wrong per the implied requirement. Fix recursion with a static Set<Id> of processed records — not a boolean, which breaks on multi-chunk batches over 200 records. Better yet, ask whether a before-update assignment removes the DML entirely.

Done when
  • Your test suite fails against the original and passes against the fix.
  • You can explain in two sentences why a static boolean guard is subtly wrong and a static Set is right.
13 · Email-to-Task logger
Working levelTask subtypesservice class designidempotency

The ticket: Straight from your real EAC world: build EmailLogService.logEmail(...) that records a sent email against a Contact as a Task with TaskSubtype = 'Email', subject, description, and activity date — and never logs the same message twice (dedupe on a caller-supplied message key stored in a custom field).

Build
  • Bulk signature: takes a list of request objects, returns per-request created/skipped/error results.
  • One query on the message-key field to find already-logged messages; skip those.
  • Fail soft: one bad request (missing ContactId) errors in its result row without sinking the batch.
The trap

TaskSubtype is write-once-on-create — you cannot flip an existing Task to an Email subtype later. And your dedupe key needs a queryable custom field; the tempting system fields in this area are read-only, as you've already discovered on the real project. Design the field, don't fight the platform.

Done when
  • Calling it twice with the same keys creates Tasks once and reports "skipped" the second time.
  • The tasks render under the Contact's Activity timeline as emails in TrentDev — go look.
14 · Config accessor with caching
Stretchstatic cachingcustom metadataconfig-driven code

The ticket: Several classes query a Partner_Config__mdt custom metadata type for tier thresholds. Build a PartnerConfig accessor class so the whole transaction reads metadata once, callers get typed values with defaults, and a bad/missing config row can't throw a null pointer three classes away.

Build
  • The custom metadata type itself in TrentDev with 3–4 rows.
  • Lazy-loading static map: first call populates, every later call in the transaction is free.
  • Typed getters with defaults: PartnerConfig.getGoldThreshold() returns a sane number even if the row is missing.
The trap

Statics reset per transaction, not per session — know exactly what that means before you rely on it. And in tests you can't insert custom metadata: either use the real rows (fine for config) or add a @TestVisible override seam. Choosing that seam consciously is the rep.

Done when
  • Two different classes call it; debug log shows one metadata query total.
  • A test proves the default path when config is absent (via the override seam).
15 · The capstone: campaign attribution sweep
Stretcheverything abovedesign docyour real domain

The ticket: Combine the tiers. A nightly job finds Campaigns missing a Refer_ID__c (your Accutics world), calls an external tagging API for each untagged campaign (mock it with httpbin), writes the returned ID back, logs failures to Integration_Log__c, and emails a summary. An invocable action lets admins trigger a single campaign's tagging from a Flow button.

Build
  • Batchable + AllowsCallouts for the sweep; Schedulable for nightly; Queueable + invocable for the one-off path — sharing one callout service class between both paths.
  • Callout limits are 100 per transaction: batch scope must respect that. State your scope size and why in a comment.
  • Write a half-page design doc first: classes, responsibilities, failure modes. Then build to it.
The trap

The single-campaign path and the sweep will drift apart unless the callout + write-back lives in exactly one service class both entry points call. If you find yourself copying a method between them, stop and refactor. This one-service/many-entry-points shape is the architecture answer to half the questions you'll ever get asked.

Done when
  • Both paths run in TrentDev against the mock endpoint; failures land in the log object.
  • Full test suite passes at 90%+ coverage without a single test that exists only for coverage.
