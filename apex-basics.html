Twelve small business scenarios. Read the ask, write the trigger, write the handler, deploy it, watch it fire. Every one is a trigger plus a handler class — nothing else. They start with one object and one field and end with recursion guards, so by the last one the Practice Reps will read like the same moves at a bigger size.

Apex Practice Reps → Progress saves automatically

How to work these

  • Always two files. A trigger that delegates in one line, and a handler class that holds the logic. Even when the logic is three lines and the split feels silly — that is the habit being drilled.
  • It does not have to be good. Nothing here ships. Skip the service layer, skip the feature flags, skip the framework. Trigger, handler, done.
  • Deploy every one. Right-click → SFDX: Deploy Source to Org, or sf project deploy start -d force-app. Then make the change in the UI and watch it happen.
  • Custom fields as you go. A few scenarios need a checkbox or number field that does not exist yet. Create it in Setup when you hit it — that is part of the rep.
  • Sandbox only. TrentDev, never production.

One object, one field

Before-triggers on a single record. No queries, no other objects — just get the two-file habit into your hands.

1 · Default the Rating on new Accounts
Start herebefore insertTrigger.new

The scenario: Partner managers keep creating Accounts with the Rating left empty, and the reports look broken. When an Account is created with no Rating, it should default to Warm.

The trigger
  • AccountTrigger on Account, before insert.
  • One line inside: AccountTriggerHandler.handleBeforeInsert(Trigger.new);
The handler
  • handleBeforeInsert(List<Account> newAccounts) loops the list.
  • If acc.Rating is blank, set it to 'Warm'. That is the whole method.
Worth knowing

No update statement anywhere. In a before trigger the record has not been written yet, so assigning the field is enough — Salesforce saves what you leave in Trigger.new.

Done when
  • You create an Account in the UI with Rating empty and it saves as Warm.
  • An Account created with a Rating keeps the one you typed.
2 · Clean up the partner code on save
Start herebefore insertbefore updatetwo contexts

The scenario: Everyone types the partner code differently — lowercase, trailing spaces, mixed case. Whenever an Account is saved, the code should end up trimmed and uppercase, no matter how it was typed.

The trigger
  • Add before update to your existing AccountTrigger.
  • Route both contexts to the same handler method — the logic is identical for insert and update.
The handler
  • normalizeCode(List<Account> accounts) — loop, and if the field is not null, set it to code.trim().toUpperCase().
  • Use any text field you like. AccountNumber works without creating anything.
Worth knowing

This is your first taste of one handler method serving two trigger contexts. Notice you did not need Trigger.old — you are not comparing anything, just cleaning whatever came in.

Done when
  • Typing abc-123 saves as ABC-123 on both create and edit.
  • Saving an Account with the field empty does not blow up with a null error.
3 · Only act when the field actually changed
Start hereTrigger.oldMapchange detection

The scenario: When a Contact's Email changes, stamp a date field with today so we know when their contact info was last touched. Editing any other field on the Contact should leave that date alone.

The trigger
  • ContactTrigger on Contact, before update.
  • Pass both collections: ContactTriggerHandler.stampEmailChange(Trigger.new, Trigger.oldMap);
The handler
  • Signature takes List<Contact> newContacts, Map<Id, Contact> oldMap.
  • For each Contact, compare con.Email to oldMap.get(con.Id).Email.
  • Only when they differ, set your date field to Date.today().
Worth knowing

This comparison is the single most reused pattern in Apex. Without it, a trigger fires its logic on every save of every record forever — which is how a simple stamp turns into a performance incident.

Done when
  • Changing the Email sets the date.
  • Changing only the Title leaves the date exactly as it was.
01

Reach to the parent

After-triggers that write to a different object. Collect ids, query once, update once.

4 · Contact phone changes → copy it to the Account
Cross-objectafter updateparent updateMap

The scenario: When a Contact's Phone is updated, push that number onto the parent Account's Phone field so the Account always shows the most recently updated contact number.

The trigger
  • ContactTrigger, add after update.
  • Delegate with Trigger.new and Trigger.oldMap.
The handler
  • Loop Contacts; skip any whose Phone did not change (drill 3's pattern) or whose AccountId is null.
  • Build a Map<Id, String> of AccountId → new phone.
  • Build a List<Account> from that map using new Account(Id = accId, Phone = phone) — no query needed.
  • One update call on the list, outside every loop.
Worth knowing

You can update a record you never queried, as long as you have its Id. Constructing new Account(Id = ...) saves you an entire SOQL query, and it is the normal way to do parent updates.

Done when
  • Editing a Contact's Phone updates the Account within the same save.
  • Editing a Contact with no Account attached does not throw.
5 · Opportunity goes Closed Won → flag the Account
Cross-objectstage changecheckboxdate stamp

The scenario: The moment an Opportunity flips to Closed Won, the parent Account should be marked as a signed partner — a checkbox ticked and a date field set to today. Once marked, later edits should not un-mark it.

Setup first
  • On Account, create Is_Signed_Partner__c (checkbox) and First_Won_Date__c (date).
The trigger
  • OpportunityTrigger on Opportunity, after update.
The handler
  • For each Opportunity, check the stage became Closed Won: new is 'Closed Won' and old was not.
  • Collect the AccountIds into a Set<Id>.
  • Build Accounts with the checkbox true and the date set to Date.today(), then one update.
Worth knowing

"Became Closed Won" is not the same as "is Closed Won." Without the old-value check, every later edit to an already-won Opportunity re-stamps the date, and your "first won" field quietly becomes "most recently edited."

Done when
  • Moving an Opportunity to Closed Won ticks the box and sets the date.
  • Editing the Opportunity's name afterwards leaves the date unchanged.
6 · Keep a live Contact count on the Account
Cross-objectafter insertafter deleteaggregate

The scenario: Account owners want a number field showing how many Contacts the Account has, kept accurate as Contacts are added and removed.

Setup first
  • On Account, create Contact_Count__c (number, 0 decimals).
The trigger
  • ContactTrigger, add after insert and after delete.
  • On insert read Trigger.new; on delete read Trigger.old — Trigger.new is null in a delete.
The handler
  • Collect affected AccountIds into a Set<Id>.
  • One query: SELECT AccountId, COUNT(Id) c FROM Contact WHERE AccountId IN :accIds GROUP BY AccountId.
  • Seed a map with 0 for every id first, then overwrite from the query results.
  • Build the Account list and update once.
Worth knowing

That zero-seeding step is the bug everyone hits. An Account whose last Contact was just deleted returns no row from the aggregate query — so without seeding, it keeps its old count forever.

Done when
  • Adding a Contact increments the count; deleting one decrements it.
  • Deleting the last Contact leaves the Account showing 0, not 1.
02

Guardrails

Triggers that stop bad data or enforce a "only one of these" rule.

7 · Only one primary Contact per Account
Guardrailone-of rulesibling update

The scenario: Each Account should have exactly one primary Contact. When someone marks a Contact as primary, every other Contact on that Account should be un-marked automatically — no error message, just make it true.

Setup first
  • On Contact, create Is_Primary__c (checkbox).
The trigger
  • ContactTrigger, after insert and after update.
The handler
  • Find Contacts where Is_Primary__c just became true. Collect their AccountIds and their own Ids.
  • Query the siblings: Contacts on those Accounts, Is_Primary__c = true, Id NOT IN the ones just marked.
  • Set those to false and update once.
Worth knowing

Your handler updates Contacts from inside a Contact trigger, so the trigger fires again on those records. It happens to settle here because the second pass finds nothing to change — but this is exactly the setup that becomes drill 12.

Done when
  • Marking a second Contact primary silently un-marks the first.
  • An Account with three Contacts never shows two primaries at once.
8 · Block Closed Won without a primary Contact
GuardrailaddErrorbefore update

The scenario: An Opportunity must not be moved to Closed Won unless its Account has a primary Contact on file. If it does not, stop the save and tell the user why.

The trigger
  • OpportunityTrigger, before update.
The handler
  • Find Opportunities becoming Closed Won; collect their AccountIds.
  • One query for primary Contacts on those Accounts; build a Set<Id> of Accounts that have one.
  • For any Opportunity whose Account is not in that set, call opp.addError('Add a primary Contact before closing this deal.');
Worth knowing

addError on the record blocks just that record and shows the message on the page. In a 200-record load the other 199 still save — which is usually what you want, and always worth knowing before someone asks.

Done when
  • Closing without a primary Contact shows your message and does not save.
  • Adding a primary Contact then closing works.
9 · Stop deletion of Accounts with open Opportunities
Guardrailbefore deleteTrigger.old

The scenario: Accounts with open Opportunities should not be deletable. Someone cleaning up test data keeps wiping out live pipeline.

The trigger
  • AccountTrigger, add before delete.
  • Only Trigger.old exists in this context.
The handler
  • Query Opportunities where AccountId IN :Trigger.old keySet and IsClosed = false.
  • Build a Set<Id> of Accounts that have one.
  • addError on each Account in that set, naming how many open Opportunities it has.
Done when
  • Deleting an Account with an open Opportunity is refused with your message.
  • An Account whose Opportunities are all closed deletes fine.
03

The ones that bite

Reparenting, cascades, and recursion — the three things that turn a working trigger into a broken one.

10 · A Contact moves to a different Account
Trapreparentingold + new parent

The scenario: Your Contact count from drill 6 is wrong whenever someone moves a Contact from one Account to another. The old Account keeps counting them, the new one never starts. Fix it.

The trigger
  • ContactTrigger, after update — you already have it.
The handler
  • When AccountId changed, add both the old and the new AccountId to your recalculation set.
  • Pull the old one from Trigger.oldMap, the new one from the record in Trigger.new.
  • Everything downstream — the aggregate query, the seeding, the single update — stays exactly as it was.
Worth knowing

Almost every first attempt at a rollup misses the old parent. Reach for this the moment a lookup field can change: the record left something behind, and that something needs recalculating too.

Done when
  • Moving a Contact between two Accounts leaves both counts correct.
  • Moving 200 Contacts in one update still leaves both correct.
11 · Account goes Inactive → deactivate its Contacts
Trapcascadechild query

The scenario: When an Account's status changes to Inactive, every Contact on it should be marked inactive too. Changing the Account back to Active should not reactivate them — that stays a human decision.

Setup first
  • On Contact, create Is_Active__c (checkbox, default true). Use Account's standard Type or a picklist of your own for the status.
The trigger
  • AccountTrigger, after update.
The handler
  • Collect Accounts whose status became Inactive.
  • Query their Contacts where Is_Active__c = true — no point updating ones already false.
  • Set false on each, one update.
Worth knowing

Filtering the child query to only records that actually need changing is not a micro-optimisation. It keeps your DML row count down, and on an Account with thousands of Contacts it is the difference between working and hitting a governor limit.

Done when
  • Flipping an Account to Inactive deactivates all its Contacts in one save.
  • Flipping it back to Active leaves them deactivated.
12 · Stop your own trigger re-firing
Traprecursionstatic Boolean

The scenario: Make the primary-Contact rule from drill 7 misbehave on purpose, then fix it. Add a second piece of logic to the Contact handler that also updates Contacts, and watch the two bounce off each other until Salesforce throws a limit error.

Break it
  • In the Contact handler, on after update, have it set a field on the same Contacts it was handed and update them.
  • Edit a Contact. Read the error you get.
Fix it
  • Add public static Boolean hasRun = false; to the handler.
  • Return immediately if it is true; set it true before doing any DML.
  • Deploy and confirm the edit now saves.
Worth knowing

A static variable lives for one transaction, which is exactly the window you need. This is also the pattern's weakness — guarding too broadly means the trigger skips records it should have processed in a genuine second pass, which is why real frameworks make the guard per-context rather than one flag for everything.

Done when
  • You saw the recursion error with your own name on it.
  • The guard fixes it, and you can explain why a static resets between transactions.
