Twelve small drills for getting into VS Code and actually shipping something to your sandbox. No frameworks, no architecture, no handler patterns — write a file, deploy it, run it, see the result. Work these before the Practice Reps, which assume you already have the loop working.

Apex Practice Reps → Progress saves automatically

How to work these

  • It does not have to be good. Nothing here is going to production. The only failure is not opening VS Code.
  • Deploy every single one. Right-click the file → SFDX: Deploy Source to Org, or sf project deploy start -d force-app. Code that only exists locally does not count.
  • Run it and look at the output. SFDX: Execute Anonymous Apex, then read the debug log. Seeing your own System.debug come back is the whole point.
  • Sandbox only. These drills insert and delete records. Point at TrentDev, never production.
  • One sitting each. If a drill takes more than 20 minutes, you have wandered off the drill — cut it back down.
00

Close the loop

Before any Apex matters, the pipe from VS Code to your sandbox has to work.

1 · Hello, sandbox
Start heredeployExecute Anonymousdebug log

The drill: Prove the pipe works end to end. One class, one method, one debug line — written locally, deployed to your sandbox, and executed.

Build
  • In VS Code: Cmd+Shift+P → SFDX: Create Apex Class → name it HelloApex.
  • Give it one method: public static void sayHi() that calls System.debug('Hi from ' + UserInfo.getName());
  • Right-click the file → SFDX: Deploy Source to Org.
Run it
HelloApex.sayHi();
Worth knowing

If the deploy fails before you have written anything real, that is still a win — the error is about your org connection, not your code. Fix that first, because every other drill depends on it.

Done when
  • The class appears in Setup → Apex Classes in your sandbox.
  • You can find your debug line in the log output.
2 · Your first test class
Start here@isTestAssertcoverage

The drill: Apex will not deploy to production without test coverage. Learn the shape of a test now, while the thing being tested is trivial.

Build
  • Create HelloApexTest and annotate the class @isTest.
  • One method: @isTest static void testSayHi() that calls HelloApex.sayHi();
  • Add one assertion — even Assert.areEqual(1, 1); counts for today.
  • Run it: Command Palette → SFDX: Run Apex Tests.
Worth knowing

A test that asserts nothing still passes. That is the habit worth breaking early — write the assert line first, even a silly one, so the muscle is there when the code is real.

Done when
  • The test passes green in the VS Code output.
  • HelloApex shows coverage in Setup → Apex Classes.
3 · Break it on purpose
Start hereerrorsreading logs

The drill: You will read far more error messages than you write lines of code. Practice reading them while the stakes are zero.

Build
  • Delete a semicolon in HelloApex. Deploy. Read the error.
  • Rename the method in the class but not in the test. Deploy. Read that error.
  • Reference a field that does not exist, like Account.Nonsense__c. Deploy. Read that one too.
Done when
  • For each error you can point at the file and line before scrolling up to look.
  • You can tell a compile error apart from a test failure at a glance.
01

Data you hold onto

Variables and collections. Small, dull, and the foundation of everything after it.

4 · Variables and types
FundamentalsStringIntegerDecimalDate

The drill: Apex is typed — you declare what a thing is before you use it. Get the six types you will actually touch into your fingers.

Build
  • New class BasicsVars with one static method run().
  • Declare and debug a String, Integer, Decimal, Boolean, Date, and an Id.
  • Concatenate a String and an Integer in one debug line and notice what Apex does with it.
Run it
BasicsVars.run();
Worth knowing

Use Decimal, not Double, for anything involving money. Salesforce currency fields come back as Decimal, and mixing the two is a rounding bug waiting for a quarter-end close.

Done when
  • Six debug lines, all with the values you expected.
  • You know which type an Id is and why it is not just a String.
5 · List, Set, Map
Fundamentalscollectionsdedupekey lookup

The drill: Three collections. A surprising share of Apex bugs come down to having picked the wrong one.

Build
  • Build a List<String> of five names, two of them duplicates. Debug .size().
  • Pour the same five into a Set<String>. Debug .size() again.
  • Build a Map<String, Integer> of name → name length. Pull one value out by key, without looping.
Worth knowing

The Map is the one that pays off most. Nearly every "why is this so slow" Apex fix is someone replacing a nested loop with a Map lookup.

Done when
  • You can say out loud why the List and Set sizes differ.
  • You got a value out of the Map by key with no loop involved.
6 · Loops and conditionals
Fundamentalsforifrunning total

The drill: Loop a collection, make a decision inside it, and keep a running total across the iterations.

Build
  • Method that builds a List<Integer> holding 1 through 20.
  • for loop over it; if the number is even, add it to a running total.
  • Debug the total, then write it again using a for (Integer i = 0; i < 20; i++) style loop.
Done when
  • Both loop styles produce 110.
  • You know which of the two you find easier to read.
02

Talking to the database

SOQL reads, DML writes. This is where Apex stops being a toy.

7 · Your first SOQL query
Core skillSOQLSELECTloop

The drill: Read real data out of your org and prove it matches what the UI shows you.

Build
  • List<Account> accts = [SELECT Id, Name FROM Account LIMIT 5];
  • Debug accts.size(), then loop and debug each Name.
  • Open the Accounts tab and compare.
Worth knowing

SOQL only returns the fields you name in the SELECT. Touching acct.Phone when you never selected Phone throws at runtime, not at compile time — one of the most common first bugs.

Done when
  • Names in the log match the Accounts tab.
  • If you got zero rows, you knew to go create an Account first.
8 · Filter, sort, limit
Core skillWHEREORDER BYbind variable

The drill: A query with no WHERE clause is rarely the query you actually wanted.

Build
  • Query Accounts WHERE Name LIKE 'A%'.
  • Add ORDER BY Name ASC and LIMIT 10.
  • Then put a String in a variable and query WHERE Name = :myVar.
Done when
  • Three working queries, each returning what you predicted.
  • You can explain what the colon does in a bind variable.
9 · Your first DML
Core skillinsertupdatedelete

The drill: Write data into the org — insert, update, delete — and watch each one land in the UI.

Build
  • Account a = new Account(Name = 'Apex Test Co'); then insert a;
  • Debug a.Id — note it was blank before the insert and populated after.
  • Change the Name and update a;, then delete a; and go find it in the Recycle Bin.
Worth knowing

Sandbox only, never production. This is exactly the drill where a stray Execute Anonymous run goes somewhere you did not mean — check which org is connected before you hit run.

Done when
  • You watched the record appear, change, and vanish in the Salesforce UI.
  • You can explain where the Id came from and when it got set.
10 · Query, change, update as a list
Core skillbulkificationgovernor limitsDML

The drill: The single most important habit in Apex — one DML call for many records, never one call per record.

Build
  • Query 10 Accounts into a List<Account>.
  • Loop them and set Description = 'Touched by Apex'.
  • Outside the loop, call update accts; once.
  • Now write the bad version with update a; inside the loop. Run both and compare Limits.getDmlStatements().
Worth knowing

This is the difference every Salesforce interview question is fishing for. Bulkification just means: collect first, act once, outside the loop.

Done when
  • The good version uses 1 DML statement; the bad version uses 10.
  • You can state the limit from memory — 150 DML statements per transaction.
03

Your first trigger

No handler class, no framework, no architecture lecture. Make a trigger fire, then test it.

11 · A trigger that fills in a blank
Putting it togetherbefore insertTrigger.new

The drill: See a trigger fire. The smallest possible one that does something you can actually see in the UI.

Build
  • SFDX: Create Apex Trigger → AccountTrigger on Account, before insert.
  • Inside, loop Trigger.new; if a.Description is blank, set it to 'Created ' + Date.today().format().
  • Deploy, then create an Account in the UI with the Description left empty.
Worth knowing

before insert means you can just set the field — no update statement needed, because the record has not been written yet. The same logic in after insert would cost you an entire extra DML call.

Done when
  • The new Account shows your generated Description, saved with no second DML.
  • You can explain why before was the right context here.
12 · Test the trigger, then bulk it
Putting it togetherTest.startTest200 recordsassert

The drill: Prove the trigger works for one record. Then prove it still works for two hundred in a single insert.

Build
  • Test class: insert one Account with no Description, query it back, assert the Description is not blank.
  • Second method: build a List<Account> of 200 and insert them in one call.
  • Wrap the inserts in Test.startTest() / Test.stopTest(), then assert all 200 got a Description.
Worth knowing

If the 200-record test fails, you have found a real bulkification bug in your own trigger. That is not a setback — finding it yourself is the entire point of the drill, and it is the bridge to the Practice Reps.

Done when
  • Both test methods pass.
  • You understand why the 200 case is the one that matters.
